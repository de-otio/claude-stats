# Internationalisation — how it works and how not to break it

claude-stats ships **10 locales**: `en` (reference) plus `de`, `es`, `fr`, `ja`,
`pl`, `pt-BR`, `ru`, `uk`, `zh-CN`. Every user-facing string lives in
`packages/core/src/locales/<locale>/<namespace>.json`, where the namespaces are
`cli`, `common`, `dashboard`, `extension` and `frontend`.

The rule: **any change that adds or edits a user-facing string updates all ten
locales in the same change.** Translations are generated locally, never in CI.

---

## The parity check

```
npm run locales:check          # = node scripts/check-locale-parity.mjs
```

It enforces five things against `en`:

1. the same set of namespace files;
2. the same set of keys, dot-flattened — with plural categories handled per
   locale, so a Slavic locale is *required* to have `_few`/`_many` that `en`
   does not spell;
3. the same `{{placeholder}}` identifiers in every shared value;
4. the same `$(codicon)` tokens in every shared value;
5. **no growth in the number of values byte-identical to `en`**, per
   (locale, namespace), against `scripts/locale-identity-baseline.json`.

### Why check 5 exists

Checks 1–4 compare key sets, placeholders and codicons — they never look at the
**values**. So a namespace whose values are verbatim English passes clean.

That is not hypothetical. It hid roughly **1,200 untranslated strings**: whole
features (`backup`, `sync`, `archive`, `org`, `deviceSync`, `notifications`)
were added to `en`, stubbed into the other nine locales, and never filled.
Japanese was 59% identical to English in the `extension` namespace and 0.3%
identical in `frontend` — Japanese does not coincidentally match English 140
times. Every locale reported `ok` throughout, because nothing checked.

The user-visible symptom that finally surfaced it was a VS Code status bar
reading `extension:sync.status.disconnectedText`, which was a *different* bug
(see "Late i18n boot" below) that happened to point at the same namespace.

### Why a ratchet and not "no identical values"

Some identity is legitimate — brand names (`Claude Stats`, `Dropbox`,
`OneDrive`), example values (`you@example.com`), and loanwords a target
language genuinely uses. A flat rule would fire on those, and a check that
cries wolf gets bypassed.

So check 5 is a **ratchet against a committed per-(locale, namespace) baseline**:
it fails the moment a namespace gets *worse*, and never when it gets better. It
does not demand the pre-existing debt in `cli`/`dashboard`/`common`/`frontend`
be cleared before you can merge — it only stops NEW untranslated strings.

Values with no translatable letters once `{{placeholders}}` and `$(codicons)`
are stripped (`—`, `100%`, `$(sync~spin)`, `{{count}}`) are exempt and never
counted. That was chosen over a per-key allowlist deliberately: an allowlist
has to be curated, and forgetting to add to it produces a false alarm.

### When the check fails

```
extension.json: 15 values are identical to en (baseline allows 13)
  — 2 newly untranslated string(s).
```

Either fill them (below) or, if the identity is genuinely legitimate,
re-baseline and say why in the commit message:

```
node scripts/check-locale-parity.mjs --update-baseline
```

When you fill translations, the check prints a note telling you the ratchet can
be tightened. **Tighten it** — that is what keeps the guarantee meaningful:

```
note: 27 baselined identical value(s) are now translated —
      run with --update-baseline to tighten the ratchet.
```

## Filling translations

`scripts/fill-locales.mjs` shells out to `claude -p` (headless Claude Code, one
subprocess per locale × namespace, chunked so a large namespace cannot time out
as a unit). It uses your logged-in session, not `ANTHROPIC_API_KEY`.

```
node scripts/fill-locales.mjs --dry-run                      # report, call nothing
node scripts/fill-locales.mjs --locale=de                     # one locale
node scripts/fill-locales.mjs --namespace=extension           # one namespace
node scripts/fill-locales.mjs --force                         # also redo values equal to en
node scripts/fill-locales.mjs --max-budget-usd=1.00           # per-batch cap (default 1.00)
```

Working practice:

1. `--dry-run` first, to see the scope.
2. Run **one locale**, read the diff, and confirm placeholders, codicons and
   brand names survived before fanning out.
3. Scope with `--namespace` when the gap is concentrated. `--force` retranslates
   *everything* identical to `en`, including the legitimately-identical values —
   which can turn correct strings into wrong ones, so prefer a narrow scope.
4. Never hand-translate a large batch inline.

## Late i18n boot (`onI18nReady`)

`activate()` in `packages/cli/src/extension/extension.ts` kicks off `initI18n()`
asynchronously and then constructs status-bar owners **in the same synchronous
tick**. Until that promise resolves, `extension/i18n.ts`'s `t` is a passthrough
that returns the key verbatim.

So any component that **paints once in its constructor and then sits there**
renders raw keys — permanently, if it has no other reason to repaint. That is
what put `extension:sync.status.disconnectedText` in a user's status bar.

`onI18nReady(cb)` is the fix: it runs `cb` when translations land, or
immediately if they already have, and returns an unsubscribe to push onto the
component's `disposables`.

```ts
const unsubscribe = onI18nReady(() => this.updateStatusBar());
this.disposables.push({ dispose: unsubscribe });
```

Guard the relabel if the component may have real content by then —
`StatusBarManager` keeps a `hasStats` flag so a late boot cannot overwrite
numbers that already arrived.

Components audited as **not** needing it, because they are created on demand
after activation or run inside `initI18n().then()`: `panel.ts`, `sidebar.ts`,
`mcp-register.ts`, `backup-onboarding.ts`.

For tests that need the pre-i18n state, call `__resetI18nForTests()` and restore
in `afterEach` — see `packages/cli/src/__tests__/extension-i18n-late-boot.test.ts`.
Note that `packages/cli/src/__tests__/setup.ts` seeds the extension `t()` for
every CLI test and loads locale JSON from **source**, not `dist`.

## Decision record

**The team-sync status-bar item stays visible unconditionally** (2026-09-01).

`SyncManager.updateStatusBar()` ends in an unconditional `show()`, so a user who
has never opted into team sync still sees a `$(cloud-upload) Sync Off` chip.
Hiding it until configured, or gating it behind a new `claude-stats.showSyncStatus`
setting, were both considered and declined: the chip is how a user discovers team
sync exists, and post-fix it is a correct, localised label with a working tooltip.
This is polish, not a bug — revisit only if users report the chip as noise.
